**版本：** 1.0
**更新日期：** 2026-09-16

## 1. 项目技术目标与验收范围

本项目的技术目标不是简单生成供应商风险摘要，而是在采购业务中建立一条受控链路：

```text
采购问题 / 日报提醒
  → 身份与责任范围校验
  → 任务规划与多源检索
  → 证据、数据覆盖与结论生成
  → 风险复核 / 替代寻源建议
  → 人工审批、执行回执与审计留痕
```

本次验收覆盖以下范围：

| 验收范围 | 核心判断 |
| --- | --- |
| 业务正确性 | 是否能完成风险复核、连续追问、寻源候选分层和复核闭环 |
| 数据可信性 | 是否展示来源、时间、覆盖状态和待核验项，且不把缺失数据表述为低风险 |
| 权限与安全 | 是否按责任范围隔离数据；写操作是否经过人工审批 |
| Agent 运行可靠性 | 是否能处理多工具、部分失败、超时、断线和恢复 |
| 前端可用性 | 是否能展示任务状态、证据、候选、审批和错误/降级状态 |
| 部署可运行性 | PostgreSQL、MongoDB、Redis、Checkpoint、SSE 和浏览器核心路径是否可验收 |
| 业务成效 | 真实工时、返工率和满意度是否已通过试点采集；当前作为后续试点指标，不与工程验证混用 |

## 2. 技术架构与关键实现

### 2.1 架构分层

| 层级 | 组件 | 主要职责 |
| --- | --- | --- |
| 交互层 | React 19、Vite、Tailwind、TanStack Query | 采购工作台、AI 采购助手、风险监控、寻源建议、供应商库及任务/证据/审批展示 |
| 接入层 | FastAPI、JWT、责任范围依赖、SSE、WebSocket | 认证、请求接入、权限控制、流式输出和实时通知 |
| 编排层 | LangGraph Harness Runtime、PostgreSQL Checkpoint | 会话、任务、预算、依赖、有限补偿、暂停恢复和运行状态持久化 |
| 模型与工具层 | DeepSeek OpenAI 兼容接口、LangChain、ToolRegistry、ToolExecutor | 意图理解、任务规划、工具协议、输入输出校验、超时/重试/幂等策略 |
| 证据与答案层 | Claim、Evidence、EvidenceLedger、AgentAnswer | 汇总工具事实，校验证据覆盖，生成可解释的采购语言结论 |
| 数据与运行层 | PostgreSQL、MongoDB、Redis、APScheduler | 控制面事实、业务快照、证据、缓存、限流、定时任务和通知 |

### 2.2 当前活动 Agent 路径

普通聊天和只读分析统一进入 LangGraph Harness Runtime，不按旧模式切换运行内核。主要步骤为：

```text
load_session
  → resolve_turn
  → build_plan
  → execute_ready_tasks
  → validate_evidence
  → [remediate → execute_ready_tasks，最多有限补偿]
  → render_answer
  → persist_turn
```

涉及加入监控、移出监控、确认外部主体等业务状态变更时，使用独立的受控链路：

```text
ActionProposal
  → LangGraph interrupt()
  → approval_required
  → 人工批准 / 拒绝
  → Command(resume=...)
  → ToolExecutor 执行
  → 回执、审计与页面状态更新
```

### 2.3 关键技术控制点

| 控制点 | 实现原则 | 验收要求 |
| --- | --- | --- |
| 会话一致性 | 每轮请求只加载一次 execution context；新寻源任务不能复用旧物料和候选 | 连续追问能承接对象；切换品类后不返回上一轮候选 |
| 对象确认 | 名称只用于检索；稳定绑定依赖供应商代码、统一社会信用代码或已确认身份 | 主体不确定时停在待确认状态，不自动绑定相似名称 |
| 责任范围 | API、统一工具执行器和数据访问均执行范围校验 | 采购员不能读取或修改非本人责任范围对象 |
| 证据契约 | 结论必须关联 Claim、Evidence、来源、时间和覆盖状态 | 无证据、冲突、过期和未覆盖不能渲染成确定性低风险结论 |
| 工具治理 | 工具注册读写属性、审批策略、超时、重试和幂等要求 | 图和服务层不得绕过统一工具执行策略 |
| 写操作控制 | 分析与业务写入分离；写入必须经 Proposal 和审批 | 拒绝审批不产生写入；批准后有回执与审计 |
| 运行恢复 | Run 事件持久化，SSE 使用 Last-Event-ID 回放 | 刷新或短断后可继续查看既有进度和结果 |

## 3. 课题难度与攻关可验证性

项目难点来自采购业务边界与系统可靠性，而非单一模型调用。每项难点均要求有实现、测试和页面表现三类证据。

| 难点 | 典型风险 | 解决机制 | 可验收证据 |
| --- | --- | --- | --- |
| 多源信息冲突与缺失 | 同一供应商的不同来源时间不同、字段不同或数据不存在 | Claim/Evidence、数据覆盖状态、事实与建议分层 | 风险详情、Agent 回答、缺证据场景测试 |
| 多轮自然语言任务 | 追问丢失对象，或切换需求后沿用旧候选 | 执行上下文快照、任务矩阵、新任务重置、实体收敛 | 多轮追问、跨品类寻源、澄清恢复测试 |
| 主体、责任与候选边界 | 相似名称误绑定；外部候选被误认为正式供应商 | 主体确认门禁、责任范围校验、候选来源分层 | 主体待确认、越权、候选卡与供应商库验收 |
| AI 写操作风险 | 自动加入/移出监控或重复写入 | Proposal、审批中断恢复、幂等执行和审计 | 批准、拒绝、重复提交和回执测试 |
| 长链路稳定性 | 外部工具慢、部分失败、页面刷新后结果丢失 | 执行预算、有限补偿、部分完成状态、SSE 回放 | 超时/失败降级、Run 恢复、断线回放验收 |
| 演示与生产口径 | 数据源变化影响演示；冻结数据掩盖数据缺口 | 演示数据冻结、固定问题、来源与边界提示 | 演示检查清单、浏览器截图、投递/数据源记录 |

问题、根因、修复方案和回归结果以 [问题与修复记录](../issue-log.md) 为准。该记录遵循“先登记问题、再修复、后验证”的管理规则。

## 4. 验收策略与执行顺序

### 4.1 四层证据

| 层级 | 证明什么 | 典型证据 | 不证明什么 |
| --- | --- | --- | --- |
| 代码与单元测试 | 单个函数、契约和组件按预期工作 | pytest、Vitest、TypeScript、ESLint | 不证明真实服务或业务提效 |
| 图级与 Agent E2E | 任务编排、审批恢复、证据链路正确 | `agent_e2e`、离线 Eval、固定输入输出 | 不等同于真实外部数据稳定性 |
| 真实服务与浏览器 | API、数据库、SSE、登录和页面可完成核心场景 | health check、HTTP/SSE、Playwright/浏览器验收、截图 | 不代表已完成长期业务试点 |
| 业务试点 | 真实人员是否节省时间、减少返工、提升满意度 | 同类任务前后对比、访谈、任务日志 | 不能由开发自测替代 |

### 4.2 验收前置条件

1. 部署版本、Git 提交号、环境地址和验收日期已记录；
2. 前端、后端、PostgreSQL、MongoDB、Redis 和 PostgreSQL Checkpoint 就绪；
3. 使用经授权的测试账号，且已配置可验证的责任范围；
4. 演示数据冻结状态、外部数据源状态和通知开关已记录；
5. 需要写操作的场景使用明确的测试对象；不得对未授权业务对象执行真实变更；
6. 验收过程发现问题时，先登记到问题记录，再进入修复与回归。

### 4.3 核心业务验收用例

| 编号 | 场景与输入 | 预期结果 | 关键证据 |
| --- | --- | --- | --- |
| AC-01 | 登录并进入采购工作台 | 账号角色生效，只展示责任范围内的数据 | 登录响应、工作台截图、责任范围记录 |
| AC-02 | `查看一下青岛三祥科技股份有限公司的风险情况` | 返回对象明确的风险结论、依据或数据边界 | AgentAnswer、Claim/Evidence、SSE 事件 |
| AC-03 | 在 AC-02 同一会话追问 `风险结论主要依据哪些数据？` | 承接同一供应商，展示来源、时间或覆盖说明 | 会话状态、页面回答、证据引用 |
| AC-04 | 继续追问 `这家供应商下一步建议怎么处理？` | 给出继续观察、补充核验或进一步复核等建议；不自动改变业务状态 | 建议动作、审批边界说明 |
| AC-05 | `找一下安全带的供应商` | 候选按历史合作、正式供应商和外部待核验等状态分层 | 候选来源、匹配品类、主营产品、待核验项 |
| AC-06 | 外部候选确认或加入监控 | 未确认前不写入；确认后进入审批与可追溯执行链路 | 审批卡、回执、审计记录 |
| AC-07 | 非责任范围供应商查询 | 拒绝访问或返回明确权限提示，不泄露对象数据 | API 响应、页面状态、审计记录 |
| AC-08 | 数据源缺失、工具失败或证据不足 | 显示未覆盖/部分完成/暂不可用，不输出无依据低风险结论 | 降级结果、证据覆盖状态 |
| AC-09 | SSE 中断后刷新或重连 | 同一 Run 可回放未消费事件，不重复执行写操作 | Run 状态、Last-Event-ID、页面恢复记录 |
| AC-10 | 日报或通知机制 | 按责任范围生成待投递内容；真实送达以投递记录为准 | 调度日志、投递记录、脱敏消息截图 |

### 4.4 工程质量门槛

每次发布或比赛演示前，至少执行与本次变更相关的检查：

```bash
# 后端：在 backend 目录执行
python -m pytest -m "not integration" -q
python -m pytest -m agent_e2e -v

# 前端：在 frontend 目录执行
npm run lint
npm test -- --run
npm run build

# 仓库根目录执行
git diff --check
```

需要验证真实链路时，在服务健康后补充：

- 登录与责任范围验证；
- 至少一条风险复核、多轮追问和寻源候选分层；
- 至少一条主体确认/审批路径；
- SSE 断线回放或刷新恢复；
- 浏览器页面、控制台和网络错误检查。

> 测试总数会随版本演进变化。提交材料中应引用“日期、命令、通过/失败/阻塞、报告位置”，不要把历史某次测试数量作为永久产品能力。

## 5. 验收记录模板与通过准则

### 5.1 单条场景记录模板

| 字段 | 填写要求 |
| --- | --- |
| 验收编号 | 例如 AC-03 |
| 验收日期与环境 | 日期、地址、版本/提交号、数据冻结状态 |
| 验收角色 | 采购员、科室经理或管理员 |
| 前置数据 | 供应商、物料、责任关系和数据源状态 |
| 操作步骤 | 页面、输入、点击和审批动作 |
| 期望结果 | 引用本文件的场景预期 |
| 实际结果 | 页面状态、关键字段、截图或日志位置 |
| 结论 | 通过 / 失败 / 阻塞 / 不适用 |
| 异常处理 | 问题记录编号、修复版本和回归结果 |

### 5.2 发布/演示通过准则

满足以下条件可判定为“可演示、可小范围试点”：

1. 核心页面可登录、可访问，且责任范围控制有效；
2. AC-02 至 AC-05 的只读核心链路可完成，结果包含对象、依据/边界和下一步；
3. AC-06 至 AC-09 的安全与恢复场景至少完成一次有效验证；
4. 前后端构建、相关自动化回归和 `git diff --check` 通过；
5. 已知问题均已登记；高风险问题没有被隐藏为“已通过”；
6. 未将演示数据、冻结数据或开发自测写成真实生产提效结果。

以下情况不得判定为通过：

- 写操作绕过审批或越过责任范围；
- 缺失/冲突证据被描述为低风险或已验证；
- 外部待核验候选被当作正式供应商；
- 运行中断后重复执行同一业务写入；
- 关键环境健康检查失败且未标记阻塞。

## 7. 后续业务试点测量方案

工程与浏览器验收通过后，建议选择 5—10 个同类采购任务开展短周期试点，统一记录：

- 从收到风险提醒到形成处理结论的耗时；
- 每个任务查询的数据源数量和人工补充次数；
- 因信息不全导致的返工次数；
- 从风险发现到复核任务闭环的时长；
- 寻源候选清单形成时长、候选进入人工核验的比例；
- 采购人员对结论可解释性、使用便利性和结果可信度的评分。

试点结果应与原有流程的同类任务对比，并在结论中明确样本量、时间范围、角色和数据边界。
