## 2. 项目应当实现的用户结果

当前定位聚焦三个问题：我负责的供应商发生了什么变化；依据是什么、下一步需要核实什么；某物料有哪些历史合作供应商和外部待验证候选。它不承担自动准入、自动采购决策或飞书主数据维护。

| 项目目标 | 当前判断 | 原因 |
| --- | --- | --- |
| 减少查找、整理供应商信息的时间 | 具备实现基础，实际收益未测 | 自然语言入口、多来源查询、画像和证据展示已存在 |
| 发现本人/科室供应商风险变化 | 部分符合 | 稳定监控对象、快照、规则告警和责任过滤已存在；未知与陈旧数据的优先级不足 |
| 让结论可追溯且可信 | 部分符合，需优先修正 | 技术证据链完整度提升，但部分规则把样本、代理指标或缺失数据包装为过强结论 |
| 给出可继续核验的寻源候选 | 部分符合 | 来源分层、身份核验与硬门槛正确；单个不明候选可能阻塞整批，任务交接不连续 |
| 支持采购员与科室经理协作 | 未完整达成 | 供应商读取支持科室范围，复核任务却限发起人或管理员 |
| 完成风险事项处理与结果跟踪 | 仅技术执行层具备基础 | 创建、审批、执行、证据记录已存在；处理负责人、期限、搁置/关闭和效果验证没有形成完整产品流程 |
| 判断产品是否创造业务价值 | 尚未达成 | 缺少耗时、有效告警、候选可用性、处置结果等业务指标基线 |

## 4. 优先问题与可复核证据

以下编号均对应 issue-log 中的 `ISS-20261022-xxx`。P1 表示正式业务推广前应解决的可信度或关键流程问题；P2 表示应进入近期迭代的效率和治理问题。没有依据本轮离线评审宣称生产级 P0 事故。

### 016 / P1：合规“正常”建立在样本未命中上

制裁服务有固定样本数组；没有命中就返回 `clean=true`。画像直接将该值展示为“正常”。离线空来源返回 low/clean；一个虚构的“长江离线审查样本零部件有限公司”仅因短别名“长江”就匹配到内置记录并得到 critical。

这是匹配策略的反例，不是对名单中真实企业的法律状态作判断。未联网核验任何名单内容。

应提供覆盖不足、疑似命中、确认命中和覆盖范围内未命中；必须保留名单版本、来源时间与适用范围，样本不进入正式判断。

### 017 / P1：质量与交付缺少明确的指标口径

离线实测如下：

| 输入 | 当前输出 | 需要解决的问题 |
| --- | --- | --- |
| 合格率 0.952 | 风险分 4.8，low | 95.2% 是否低风险需要业务确认；不能沿用通用损失率分档 |
| 合格率 95.2 | 风险分 0，low | 百分数被直接夹到 1，需转换或明确拒绝 |
| 不良率 0.048、收货数量 10000 | 风险分 0，low | 比例再次除以数量，量纲错误 |
| 100 件合格率 50%；9900 件合格率 100% | 平均合格率 75% | 若件数就是检验分母，应汇总为 99.5%；当前连数量也被取均值 |
| 准时率 70% | 风险分 30，medium | 必须由业务确认交付阈值和样本量，不能拿未来设计中的演示阈值直接判现行实现错误 |

建议先冻结指标定义、单位、分母、统计窗口和规则版本，再调整风险标签。缺少分母时保留源系统指标，不伪装成自行重算。

### 018 / P1：同名分数在前后端被反向解释

运营服务是“分数越高风险越大”，通用 Claim 卡却把所有 `risk_score` 解释为“越高越安全”。当前原函数探针中，quality=4.8 显示“高风险信号”，delivery=90 显示“风险较低”。

需要在保持现有 API 兼容的前提下，明确分数类型、方向、维度和版本，并保证摘要、详情、颜色和报告一致。不能只改一个文案。

### 019 / P1：“审批”没有实现文档中的经理协作

供应商读取层已经支持经理科室范围，但任务查看、审批、执行都先判断“是否管理员或发起人”。所以非管理员经理不能接手采购员的任务，发起人却能自行批准。

自确认对低影响操作可能完全合理，但应叫“确认执行”；经理审批需要独立的角色/动作政策。产品需定义谁看、谁处理、谁审批，不能把三者都等同任务创建人。

证据：[任务权限](/Users/zhouminhao/Projects/work/AI_team/SuppliSense/backend/app/domains/alert/review_tasks.py:60)、[审批入口](/Users/zhouminhao/Projects/work/AI_team/SuppliSense/backend/app/domains/alert/review_tasks.py:257)、[经理供应商范围](/Users/zhouminhao/Projects/work/AI_team/SuppliSense/backend/app/domains/supplier/access.py:53)。

### 020 / P1：分析任务结束不等于风险事项关闭

覆盖核验执行只把缺失项记录为证据，返回 needs_review；页面下一步是再次发起复核。没有在同一事项中安排责任人、期限、搁置原因和业务处理回执。反复点击可以增加任务，却不一定增加业务进展。

建议区分查询执行、覆盖限制和风险事项。覆盖问题优先自动重采集或交给数据源负责人；不可得时明确边界。业务事项允许记录外部处理凭据和关闭原因，不必建设完整采购执行系统。遵循已有决定，不把资料缺口强制转嫁给采购员。

证据：[覆盖核验执行](/Users/zhouminhao/Projects/work/AI_team/SuppliSense/backend/app/domains/alert/review_tasks.py:349)、[复核页面](/Users/zhouminhao/Projects/work/AI_team/SuppliSense/frontend/src/components/MonitoringView.tsx)。

### 021 / P1：一个未知候选拖住整批寻源

审核组件要求每个候选都有确认结果；存在没有身份选项的候选时，提交按钮被禁用，又没有“排除此候选”。后端也在任何 pending 存在时整体暂停。

应按候选隔离：已确认候选可以继续，未确认候选单独保留；允许有记录地排除。不能为绕过阻塞自动绑定未知主体。

### 022 / P2：寻源历史与跨页面操作没有统一任务上下文

推荐入口创建 agent run，兼容入口历史查询 sourcing request。推荐任务可以通过当前 URL 恢复，但用户离开该地址后，没有对应的统一任务历史入口。候选继续风险核验/加入监控的跳转只传名称句子，没有传原 run、candidate/company ID 和需求范围。

### 023 / P1：覆盖完整不等于数据仍有效

监控摘要主要判断“记录是否存在”。离线提供 2020 年快照、2019 年财务和旧舆情，加上交易可用标记，仍得到 5/5 可用并建议继续观察。

每个维度需要业务时间、采集时间和有效期；过期、失败、未配置、无结果必须分别显示。寻源策略已有 freshness 规则，因此问题是当前监控摘要没有统一消费时效，并非整个项目没有任何时效设计。

### 024 / P2：首页强调展示，未充分服务每日优先级

### 025 / P1：规则信号被表达为概率，未知影响被表达为可控

预测器是规则加分，并非经过本轮可见校准证据支持的概率模型。离线 95/95/95 也触发“持续下降”。情景模拟在没有依赖数据和风险快照时，使用默认值形成 15 分、“影响轻微”和“当前影响可控”。

先称“规则预警信号”；缺少影响数据时明确无法量化。若要提供 6–12 个月预测，应先定义预测事件、历史样本、时间窗口、误报漏报和校准方法。规则方法也可以有效，但必须验证，不能靠能力名称建立可信度。

### 027 / P1：ESG 原始事实与推断标签混淆

全部诉讼数被标为“劳动/社会纠纷”，高负债被用于环保投入压力加分。诉讼不一定是劳动争议，财务压力也不是已核实环保事件。

保留已有总体数据不足门槛；明确原始事实、分类结果和推断假设。只有有案由分类依据才形成劳动纠纷指标，代理指标应单独说明限制并验证。

证据：[ESG 服务](/Users/zhouminhao/Projects/work/AI_team/SuppliSense/backend/app/domains/risk/esg_service.py:19)。

### 028 / P1：报告不能稳定复现用户刚看到的结论

报告重新读实时仓储，没有绑定本轮评估版本、来源清单和业务截至时间；HTML 按另一套司法条件取主题色，生成时间写“自动生成”，没拿到财报就写“非上市公司”。

采购人员会将报告转发给经理或留档，因而应与页面同源，并携带主体、评估 ID、规则版本、证据时间、缺失状态和真实生成时间。无财报与非上市必须分开。

证据：[报告生成](/Users/zhouminhao/Projects/work/AI_team/SuppliSense/backend/app/domains/risk/report_service.py:132)。

### 029 / P2：高级分析名称强于实际支持范围

宏观地区分值是固定配置，替代建议以行业字符串和企业安全分筛选。它们能帮助发现背景线索，但不能确认当前地区评级，也不能验证某物料的规格、资格、报价、产能承诺或到货时间。

将其定位为“宏观关注标签”“待验证同行候选”，并复用寻源核验标准。直到实际数据支撑时，再承诺具体替代方案。

证据：[地区规则](/Users/zhouminhao/Projects/work/AI_team/SuppliSense/backend/app/domains/risk/macro_service.py:66)、[替代建议](/Users/zhouminhao/Projects/work/AI_team/SuppliSense/backend/app/domains/risk/alternative_service.py:45)。

### 026 / P2：没有度量目标达成的业务验收标准

当前指标能回答调用次数、耗时和告警数，不能回答采购人员节省多少时间、多少告警值得处理、多少候选真正可用。不能用更多工具、更多报告或更多告警作为成功指标。

建议建立下列口径，先测基线再由业务设目标，不在没有数据时承诺提升比例：

| 指标 | 建议口径 | 防止误读 |
| --- | --- | --- |
| 单次复核耗时 | 同类任务从开始到用户确认结论的耗时中位数/P90，与人工基线比较 | 工具完成不等于用户复核完成 |
| 有效告警率 | 人工复核后确认需关注的告警 / 已复核告警 | 同时报待复核数，不能靠减少复核提高比例 |
| 关键事件漏报率 | 独立历史事件集中未及时发现的事件 / 已知应发现事件 | 需独立事件集，不能只检查已产生告警 |
| 候选可用率 | 用户确认值得继续商务/技术核验的候选 / 已人工评审候选 | 可用线索不等于准入或成交 |
| 事项按期完成率 | 截止期内有处理回执的事项 / 到期应处理事项 | 执行成功、风险解除分别计算 |
| 有效数据覆盖率 | 身份明确且关键证据在有效期内的监控对象 / 当前责任范围对象 | 不能按有记录就计覆盖 |
| 实际采用 | 有上述有效结果的采购员数及持续使用情况 | 登录和发送问题不能单独代表价值 |

证据：[需求说明书](/Users/zhouminhao/Projects/work/AI_team/SuppliSense/docs/requirements-specification.md)、[现有指标](/Users/zhouminhao/Projects/work/AI_team/SuppliSense/backend/app/core/metrics.py)。

## 6. 对零件/工厂运营风险设计的判断

工作区的运营设计采用供应商×物料×工厂×周期，并把交付、质量、库存供给、行动审批、执行回执和后续效果分开。它比企业整体分数更贴近“哪里会出问题、影响哪笔需求、下一步怎么办”，方向合理。

但这是范围明显扩大的下一阶段：当前活动运营契约仍围绕 company_name 和月度快照，风险维度中没有库存。不能把“收货记录数、结算金额、同行企业”视作已具备订单履约、质量批次、库存供需和可用替代供货事实。

建议以一个供应商、一个真实物料/工厂关系、一个维度开始验证。先确保事实可对账、指标可重算、负责人可接手、回执可查询，再扩展其余维度。开发合成样本应始终明确不可用于正式决策，审批本身不能让历史风险下降。

这条演进不要求推翻现有 Harness、主数据身份或责任隔离。优先复用这些基础，新增精确业务范围和来源契约。

## 7. 建议迭代顺序与验收门槛

| 顺序 | 工作 | 业务验收门槛 |
