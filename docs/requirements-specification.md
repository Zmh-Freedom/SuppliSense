# SuppliSense 需求说明书

**项目名称：** SuppliSense 供应商风险监控与智能寻源
**版本：** 0.3.0
**需求基线日期：** 2026-09-11
**文档状态：** 当前实现基线；后续需求变更需同步更新本文件和验收用例

## 1. 编写目的

本文档定义 SuppliSense 的业务目标、用户角色、功能需求、数据需求、非功能需求、边界条件和验收标准，作为产品评审、开发实现、测试验收和发布检查的共同依据。

## 2. 产品定位与范围

SuppliSense 为采购人员提供供应商风险监控和智能寻源辅助能力。系统必须输出证据、来源和数据边界，不能把模型生成内容直接当作采购决策或供应商准入结果。

### 2.1 范围内

- 供应商主体搜索、确认和监控对象管理；
- 多来源风险证据查询、整理和结构化呈现；
- 按责任范围查询供应商、监控对象、风险变化和待复核事项；
- 按物料/品类召回历史供应商、正式供应商和外部候选；
- 供应商画像、风险趋势、财务、舆情、合规、ESG 和关联关系展示；
- 风险告警、站内通知、实时推送和飞书逐人消息；
- 加入/移出监控等写操作的人工审批、执行结果和审计；
- 用户认证、角色控制、数据隔离、任务持久化和断线恢复。

### 2.2 范围外

- 自动准入、自动淘汰、自动切换供应商；
- 自动将外部候选写入正式供应商主数据；
- 无证据的确定性风险判断；
- 仅凭企业名称完成主体绑定；
- 以收货记录数推断零件数量或交付能力。

## 3. 用户角色与使用场景

| 角色 | 目标 | 关键场景 |
| --- | --- | --- |
| 采购员 | 快速复核本人负责供应商，发现风险并采取后续动作 | 查看本月风险变化、处理告警、寻找替代候选 |
| 科室经理 | 了解团队范围内风险和待办 | 查看科室供应商风险、审批或跟进复核任务 |
| 管理员 | 维护账号、数据源、责任分配和系统稳定性 | 用户管理、飞书同步、运维检查、审计和发布 |

## 4. 功能需求

### FR-01 用户认证与会话

1. 系统应支持用户名密码登录、退出和当前用户信息查询。
2. 系统应使用短期访问令牌和刷新机制；Web 前端默认使用 HttpOnly Cookie 保存访问令牌。
3. 禁用用户不得登录或继续使用受保护接口。
4. 登录、注册、刷新等认证接口应具备频率限制。
5. 用户修改密码时必须校验原密码。

**验收：** 正确账号登录成功；错误密码返回明确错误；禁用账号被拒绝；退出后受保护页面不可继续访问。

### FR-02 角色与责任范围隔离

1. 系统应支持采购员、科室经理和管理员角色。
2. 责任分配应来源于飞书责任表并同步为本地快照。
3. 采购员只能访问本人负责的正式供应商及其关联监控、告警和通知。
4. 科室经理只能访问所属科室采购员的范围。
5. 管理员可访问全量数据和运维功能。
6. 正式供应商工具、监控工具、通知接口和写操作都必须执行授权校验。
7. 缺少身份、身份格式非法或无法确定责任关系时，系统必须拒绝访问或返回受限结果。

**验收：** 使用两个不同采购员账号交叉查询，不能读取或修改对方范围内的数据；管理员访问全量成功；越权行为进入审计记录。

### FR-03 采购助手与 Harness Runtime

1. 用户应可通过自然语言发起供应商风险、范围查询、趋势、舆情、报告和寻源问题。
2. 所有只读聊天请求应进入唯一 Harness Runtime，不得通过 mode 参数切换活动执行内核。
3. 系统应在每轮请求中只加载一次执行上下文，并供路由、澄清和图节点共同使用。
4. 系统应将请求解析为可追踪任务，并通过统一 ToolRegistry/ToolExecutor 执行工具。
5. 工具执行应记录输入校验、状态、耗时、错误和结果摘要，但不得暴露模型隐藏推理。
6. 系统应返回结构化结论、Evidence、Claim、数据限制和建议动作。
7. 无法识别主体、参数不足或范围不清时，系统应先澄清，不得猜测绑定对象。
8. 证据不足时，系统应区分“资料待补充”“主体待确认”“发现信号需人工复核”和“执行失败”。
9. 系统应支持受限补证循环；达到预算或无新数据源时必须停止并说明原因。

**验收：** 同一问题可看到任务、工具、证据和终态；证据不足时不生成确定性结论；常见范围问题能生成专用任务；内部工具名不直接作为采购用户的默认展示文案。

### FR-04 风险监控与主体确认

1. 用户应可输入企业名称、统一社会信用代码、天眼查链接或供应商代码发起调查。
2. 系统应展示主体候选及可用于核对的身份信息。
3. 用户确认主体后，系统应创建带稳定 ID 的监控对象。
4. 未确认主体时不得将名称相近企业自动绑定为监控对象。
5. 监控详情应展示风险结论、证据、数据覆盖、趋势、告警和复核任务。
6. 系统应支持加入、移出监控及重新评估等操作。
7. 会改变业务状态的操作必须支持人工审批、执行结果和审计。

**验收：** 正确主体确认后能打开详情；主体信息不足时停留在待确认状态；审批拒绝不产生写入；审批通过后可看到执行回执。

### FR-05 风险分析与证据

1. 系统应支持综合、财务、商务、经营、司法、合规、舆情、ESG、供应链关系和趋势等风险维度。
2. 每个重要 Claim 应关联来源、数据时间、事实路径或工具证据。
3. 系统应展示数据覆盖状态和待补充资料。
4. 对于非上市企业或报告期不足的主体，系统应明确说明财务数据或财务趋势不可用。
5. 采购月度数据只能用于定义范围内的交易连续性、金额或收货记录变化，不得扩展解释为零件数量、交付能力或最终风险结论。

**验收：** 正常、异常、缺失和冲突数据在界面上有不同状态；用户可以从结论回到证据来源；缺失数据不显示为“未见异常”。

### FR-06 智能寻源

1. 用户应可按物料号、物料名称或品类查询供应商。
2. 结果应分层展示历史合作供应商、正式供应商和外部待验证候选。
3. 结果应标明来源、匹配依据、主体状态和待核验项。
4. 外部候选可进行企业主体和风险核验。
5. 外部候选不得自动写入正式供应商主数据。
6. 寻源结果应按用户责任范围过滤正式供应商。

**验收：** 输入物料或品类后可看到来源清晰的候选分组；候选与正式供应商不混淆；跨范围正式供应商不可见。

### FR-07 供应商库与画像

1. 系统应提供正式供应商列表、搜索和详情入口。
2. 供应商画像至少应包含概览、风险、财务、关联和日志视图。
3. 页面应显示风险评分、趋势、告警、合规计数、财务指标及数据更新时间（如有）。
4. 供应商主数据读写应受管理员或明确维护角色控制；当前活动边界以只读查询为主。

### FR-08 告警、通知与复核任务

1. 系统应根据已确认监控对象生成风险信号和告警。
2. 告警应带有严重程度、变化内容、时间和来源。
3. 通知必须按收件人或责任范围隔离。
4. 系统应支持站内通知、实时推送和可选飞书逐人消息。
5. 飞书消息应记录成功/失败、尝试次数和必要的错误信息。
6. 系统应支持创建、查询、审批、执行和查看采购复核任务。

### FR-09 数据同步与外部集成

1. 系统应支持按配置只读同步飞书供应商主数据、能力、联系人、责任分配和交易快照。
2. 同步失败不应覆盖可用的上一次本地快照。
3. 同步任务应提供状态、时间、记录数和错误摘要。
4. 天眼查、DeepSeek 和飞书均应通过环境配置启用，密钥不得写入代码或提交到仓库。

### FR-10 可观测性、审计与恢复

1. 系统应记录关键用户操作、任务状态变化、审批、工具调用和通知投递。
2. Agent 运行应持久化 Session、Turn、Run、Task、Proposal、事件和证据关联。
3. SSE 断线后，客户端应能按运行 ID 和最后事件 ID 恢复未消费事件。
4. 终态必须由服务端事件和结构化 AgentAnswer 决定，不能把部分完成或失败改写为完成。
5. 发布应提供备份、健康检查、回滚冻结和审计保留能力。

## 5. 数据需求

### 5.1 核心实体

| 实体 | 关键内容 | 事实来源 |
| --- | --- | --- |
| 用户 | 用户名、角色、状态、密码摘要 | PostgreSQL |
| 责任分配 | 供应商、采购员、科室、经理、有效状态 | 飞书同步快照/PostgreSQL |
| 供应商 | 正式供应商主数据和身份标识 | 飞书快照/业务数据 |
| 监控对象 | 稳定 ID、确认主体、责任人、监控状态 | PostgreSQL + MongoDB |
| 风险快照 | 风险评分、维度结果、覆盖范围和时间 | MongoDB |
| Evidence/Claim | 证据、事实路径、来源、验证状态 | MongoDB/运行记录 |
| Agent 运行 | Session、Turn、Run、Task、ToolCall、Proposal | PostgreSQL |
| 告警/通知 | 告警变化、收件人、投递状态和已读状态 | MongoDB |
| 寻源结果 | 物料、供应商候选、来源、核验状态 | PostgreSQL/MongoDB |

### 5.2 数据质量要求

- 记录应保留来源、抓取/更新时间和适用范围；
- 主体身份应使用稳定标识，名称只作为搜索条件；
- 缺失、超时、冲突和未覆盖必须与正常结果区分；
- 责任分配变化应可追踪，历史审计不得被物理删除替代；
- 外部候选必须保留“待验证”状态。

## 6. 非功能需求

### NFR-01 安全

- 生产环境使用 HTTPS、Secure Cookie、强随机 `SECRET_KEY` 和最小权限数据库账号；
- 密码使用安全哈希保存；
- API、工具和页面都执行认证与授权；
- 日志、SSE 和错误响应不得暴露密钥、完整 Token 或模型隐藏推理；
- 生产密钥和 `.env` 文件不得进入 Git。

### NFR-02 可靠性

- 数据库不可用时返回可识别错误，不得以空结果伪装成功；
- 外部接口超时、失败和限流应被记录并向用户说明数据边界；
- SSE 中断可恢复；重复恢复不得重复执行已确认写操作；
- Outbox、checkpoint、审计和回滚证据应保留。

### NFR-03 性能

- 普通 API 应在依赖正常时快速返回；耗时风险分析和寻源使用异步/流式反馈；
- 外部调用必须配置超时、重试和并发预算；
- Redis 用于缓存和限流，不能作为关键业务事实源；
- PostgreSQL 是 Agent 控制面唯一事实源，MongoDB 保存业务数据和证据。

### NFR-04 可维护性

- 后端按 API、领域、图、工具、服务分层；服务层保持框架无关；
- 新工具必须注册统一输入/输出、责任范围、超时、预算和证据契约；
- 前端使用 React 函数组件、TanStack Query、原生 fetch 和 Tailwind utility classes；
- 文档、问题记录、测试和发布清单随功能变更同步更新。

### NFR-05 可用性与可解释性

- 页面使用采购语言展示执行状态和数据边界；
- 结构化结果在窄屏不应横向溢出；
- 结论、证据、数据限制和建议动作应分区展示；
- 错误、澄清、部分完成、需复核和完成状态应有明确区别。

## 7. 部署与配置要求

### 7.1 运行环境

- Python 3.12；
- Node.js 20+；
- PostgreSQL 16；
- MongoDB 8；
- Redis 7；
- Docker Compose（推荐用于集成部署）。

### 7.2 外部依赖

- DeepSeek OpenAI 兼容 API：启用 AI 对话和结论生成；
- 天眼查 API：启用企业主体及风险核验；
- 飞书开放平台：启用供应商、责任分配、交易快照同步和逐人通知。

## 8. 验收基线

发布前至少应完成：

1. 登录、退出、角色和责任范围隔离；
2. 主体搜索、确认和监控对象创建；
3. 风险复核的工具、证据、Claim 和终态闭环；
4. 资料不足、主体待确认、权限不足和人工复核状态区分；
5. 历史供应商、正式供应商和外部候选的寻源分层；
6. 加入/移出监控等写操作的审批和审计；
7. SSE 断线回放、错误处理和重复提交保护；
8. 前端核心页面、TypeScript、Lint、单元测试和生产构建；
9. 后端非集成回归和 `agent_e2e` 全部通过；
10. Docker 健康检查、备份和回滚检查通过。

推荐验证命令：

```bash
cd backend
python -m pytest -m agent_e2e -v
python -m pytest -m 'not integration' -q

cd ../frontend
npm run lint
npm test -- --run
npm run build
```

## 9. 需求变更规则

以下变化必须先更新本需求说明书，再修改实现：

- 新增或改变角色、数据范围和审批边界；
- 新增外部数据源或改变来源解释；
- 修改 Agent 运行时、证据契约、SSE 事件或终态语义；
- 修改 API 返回结构、数据模型或部署依赖；
- 将当前“不在范围内”的能力纳入产品。

每次变更应关联测试、问题记录（如适用）、发布说明和回滚方案。
