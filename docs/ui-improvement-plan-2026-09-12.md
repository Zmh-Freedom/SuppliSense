# 采购寻源建议与供应商风险监控 UI 改造计划

- 日期：2026-09-12
- 状态：UI 改造已完成，真实主流程已验收；寻源主体确认仍受测试主数据边界限制
- 产品范围：为采购员提供寻源建议，监控本人负责供应商的风险变化。
- 使用方式：按阶段执行；每个阶段完成代码、验证、问题记录和关联提交后更新进度。

## 1. 目标与范围

用户进入系统后能够自然地完成两项任务：

1. 描述采购需求，找到相关供应商，理解推荐依据，并继续核验企业信息。
2. 查看负责供应商的风险变化，定位关键事件和数据缺口，执行已有复核动作。

本次包括入口、导航、寻源结果、风险监控、供应商详情、进度反馈、证据表达和视觉一致性。暂不建设完整决策系统，不新增报价、准入、复杂供应商比较、质量审核、产能预测或全生命周期管理。

不把无数据的产能、质量、交付能力包装为评分。候选企业不因被推荐而成为正式供应商。正式主数据继续只读同步。

## 2. 当前实现事实与实施边界

以下是代码核对结果；上一轮仅捕获登录页，登录后页面仍需实际浏览器验收。

| 当前实现 | 依据 | 计划约束 |
| --- | --- | --- |

| `/chat` 普通只读聊天使用 Harness | `backend/app/api/chat.py`、`graphs/harness/` | 保持唯一聊天执行入口，不增加 mode 分支 |
| `/sourcing` 主区使用 `/agent-runs` | `SourcingRiskWorkbench.tsx`、`useSourcingRiskRun.ts` | 不能直接称为 Harness 寻源 |

纠正此前讨论中的两个假设：

- Harness 和 `/agent-runs` 不是同一个运行时。是否统一后端属于独立架构变更，不能夹带在本次 UI 改造中。
- 不是所有监控操作都走同一种审批。聊天 Proposal、监控复核任务、画像直接监控接口各有现有流程；逐入口保持真实语义，成功以服务端回执为准。

## 3. 信息架构与页面方案

| 路由 | 目标页面 | 核心内容 |
| --- | --- | --- |
| `/` | 采购工作台 | 开始寻源、查看负责供应商风险、需处理事项、可恢复的最近任务 |
| `/sourcing` | 寻源建议 | 需求输入、需求摘要、业务进度、候选与来源、核验动作 |
| `/assess` | 风险监控 | 按关注优先级排列的监控对象、风险变化、覆盖、下一步 |
| `/assess/:monitorTargetId` | 监控详情 | 关键变化、事件与依据、覆盖缺口、复核任务 |
| `/suppliers` | 供应商库 | 正式供应商检索、产品信息、打开画像 |
| `/suppliers/:id` | 供应商详情 | 风险摘要、产品/能力信息、来源与联系方式、详细资料 |
| `/chat` | 采购助手 | 保留自然语言分析、历史会话、审批和断线恢复 |
| `/settings` | 设置 | 保持已有功能 |

导航优先排列“采购工作台、寻源建议、风险监控、供应商库”；采购助手保留清晰的次级入口。暂不新增独立“我的任务”页，避免新建没有统一数据支撑的模块。

现有总览中的风险排名和变化信息并入风险监控；趋势图表放在次级折叠区。是否保留独立风险总览路由，在 Phase 1 根据重复程度确定并记录。

## 4. 两条用户流程

### 4.1 寻源建议

描述物料、品类或需求 → 展示系统已理解的条件 → 必要时补充关键条件 → 搜索 → 查看相关供应商 → 阅读推荐依据与未知项 → 查看来源或核验主体与风险。

- 主输入使用多行文本，示例优先用项目已有汽车零件场景。
- 用户提供产品和不能放宽的条件；地区、数量、认证等作为选填或按需澄清。
- 系统识别出的条件允许核对；仅展示实际解析字段。后端不支持修改的条件不能做出可编辑假象。
- 使用“开始寻源”“补充需求”“查看依据”等业务文案。
- 显示“历史合作供应商”“正式供应商”“外部待核验候选”，来源未知单独说明。
- 候选首层：名称、相关产品、推荐理由、待确认事项、来源和时间、可执行动作。
- 匹配分和综合排名弱化；不能解释其口径时不作为主推荐标识。
- 相同企业避免在候选区和推荐区重复完整呈现。
- 只为有正式供应商 ID 的记录链接画像；外部候选使用任务内详情，不伪造供应商 URL。
- “核验主体”不能等同于“产品能力已验证”，分别呈现。

### 4.2 风险监控

查看负责供应商 → 找到新增风险或数据缺口 → 打开对象 → 理解变化和证据 → 查看复核建议 → 发起或处理已有复核动作 → 查看执行结果。

- 列表优先级：需处理事项、风险恶化、待首次评估/数据不足、其余对象。
- 排序使用已有结构化状态；不能按缺失分数为 0 将未知对象自动归为高风险。
- 列表显示名称、关键变化、等级、数据覆盖、更新时间、下一步。
- 详情首屏显示“发生了什么、依据是什么、需要做什么”。
- 单次快照只能说明当前情况，不能展示稳定/改善趋势。
- 保持采购员本人、经理科室和管理员的既有责任范围隔离。

## 5. 统一信息表达规则

| 信息类型 | 表达方式 | 边界 |
| --- | --- | --- |
| 来源事实 | 记录内容 + 来源 + 时间 | 来源有记录不代表已确认对供货造成影响 |
| 风险信号 | 变化 + 统计口径 + 对比周期 | 结算下降不直接推导经营困难 |
| 数据缺口 | 未覆盖/未查询/查询失败/过期 | 不转换成无风险或 0 分 |
| 系统判断 | 明确标注推断 + 支持依据 | 不把模型或规则判断标为事实 |
| 采购建议 | 具体需核实内容 | 不使用任务“完成”状态推导可正常采购 |

证据入口贴近对应结论。支持链接时打开原始来源；只有内部记录时提供可读明细和记录来源，不能伪造原文链接。业务日期、报告期、采集时间分别命名；采集时间不冒充信息发布日期。

统一安全评分方向：分数越高风险越低。总安全评分和维度风险扣分不得使用相同但未说明的标签。未知使用中性色，并同时给出文字。

业务进度只由真实事件驱动：理解需求、检索供应商、核验主体、检查风险、整理建议。澄清、失败、部分完成、审批是独立状态，不把所有终态排列成顺序时间线。没有后端候选数时不编造数量或百分比。

默认弱化 Agent、LLM、工具名称、reason code、P0、版本号和 JSON。开发诊断可保留在次级详情；审批主内容必须展示目标、动作和影响。

## 6. 后端依赖与降级策略

| 需求 | 当前可复用能力 | 缺口/核验项 | 第一版处理 |
| --- | --- | --- | --- |
| 单一寻源入口 | `/agent-runs`、Harness 聊天 | 灰度状态、权限和各入口功能不同 | Phase 0 决定可用主路径；不自动重复提交到多个内核 |
| 需求澄清 | `/agent-runs/{id}/clarification` | 前端澄清交互、字段契约 | 接入现有接口；若主路径不同按其既有澄清契约处理 |
| 恢复任务 | 按 run ID 获取详情和事件 | 运行 ID 未进入 URL | 使用 URL 参数恢复；刷新先读取服务端详情再接事件 |
| 最近任务 | 旧寻源历史、聊天历史 | 当前 agent-runs 路由没有统一列表接口 | 不把旧历史冒充新任务；仅有本机记录时明确标注并按账号隔离，必要时后置卡片 |
| 工作台待处理 | 监控对象、告警、复核任务 | 统一聚合缺失 | 聚合已有授权查询，局部错误不让整个首页失败 |
| 推荐理由 | match_reasons、reason_codes、evidence | 理由到证据未必一一关联 | 展示真实理由与“当前可用来源”；无明确关联不声称该证据支持该理由 |
| 画像来源与覆盖 | profile、monitor risk detail | profile 部分数值缺查询状态 | 不凭 0 判断无记录；只在合法关联且有权限时读取监控覆盖，否则标为未知 |
| 页面内继续分析 | `/chat?q=...` | 浮动入口只传文本，监控 URL 段实际上是 ID | 传真实名称及明确的可验证上下文；不能宣称助手已读取当前页面 |
| 监控与审批 | 现有 watch、review task、proposal 接口 | 不同入口动作语义不同 | 保留各接口确认与执行流程；失败保留用户输入和可重试状态 |

新增聚合接口、推荐理由结构化、统一任务列表均为可选补强，不作为首批 UI 发布前提。确需补强时单列任务和兼容方案，不修改已有 API 返回结构，不在 service 中引入 LangGraph。

## 8. 验收场景

| 场景 | 必须满足 |
| --- | --- |
| 首次登录采购员 | 一次操作进入寻源或本人风险监控，责任范围清晰 |
| 输入已有物料 | 显示历史/正式候选及其真实匹配依据 |
| 外部候选 | 显示待核验、来源；不伪造正式画像或已准入状态 |
| 需求不完整 | 能补充必要条件，不出现没有操作入口的澄清状态 |
| 刷新寻源页面 | 恢复同一次任务和已保存结果，不再创建新任务 |
| 部分来源失败 | 保留已获得候选，明确未完成范围 |
| 无候选 | 提示调整需求或来源覆盖，无成功推荐假象 |
| 低安全评分 | 等级、颜色、文字和风险事件方向一致 |
| 无财报/未查询司法 | 显示未覆盖或未查询，不显示财务健康/无司法风险 |
| 单条风险快照 | 不宣称稳定、改善或恶化 |
| 跨页面查看企业 | 主体一致；当前需求仅在确实传递时显示 |
| 审批与执行 | 待审批、批准、拒绝、执行中、失败、完成分别准确 |
| 账号切换 | 任务入口和查询缓存不泄露前一账号结果 |
| 键盘与小屏 | 主入口、输入、详情、证据和操作均可访问 |

自动验证使用有业务意义的状态与交互回归，避免只断言颜色类名或组件实现。前端执行 lint、实际项目 TypeScript 构建检查和相关测试；阶段收尾运行完整前端测试与构建。涉及后端时执行对应 pytest；涉及 Agent 跨流程时按项目规则补充/运行无外部服务的 agent_e2e。

真实浏览器验收使用获准的测试账号和数据。只读页面检查不触发正式监控变更；需要创建任务、核验或审批的场景使用明确的测试对象。模型等待时长如需比较，记录相同条件下的实际值，不预设改版一定更快。

## 9. 问题记录、提交与回退

每个确认问题在修复前进入 `docs/issue-log.md`，包含日期、状态、优先级、现象、影响、根因、方案、验证和关联提交。不得只在本文打勾而不补充问题验证。

每个相关功能形成独立提交，建议边界：工作台导航、寻源恢复与澄清、候选展示、风险表达、画像调整、视觉收尾。保持用户已有修改；不删除测试；不改变已有 API 返回结构。涉及后台依赖的补强单独提交并说明兼容性。

前端阶段尽量不依赖数据迁移，便于按提交回退。已有路由、历史任务读取和服务器数据保持兼容；恢复旧界面不应导致任务或风险快照丢失。
