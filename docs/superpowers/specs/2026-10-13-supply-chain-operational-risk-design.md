# 供应链运营风险功能与数据设计

日期：2026-10-13。状态：设计草案，尚未生成数据或实现功能。

## 1. 产品目标与实施边界

在 SuppliSense 中增加供应链运营风险能力。采购员从供应商总览发现异常，下钻到零件、工厂和业务单据，了解交付、质量和库存供给压力，再形成处理计划、审批、执行和效果跟踪。

业务模型、页面和工作流按可能上线的功能设计。开发阶段使用合成数据验证正常和异常业务链路；上线逐项接入已经校验的真实数据。合成数据保留来源标记，不进入正式采购证据与正式告警。功能名称为“供应链运营风险”，正式入口以供应商、零件、工厂和时间筛选，不采用预设故事作为业务分析入口。

三个场景属于同一家供应商的不同零件，同一个业务时点可以同时存在。风险等级、预算和供应商资格在样本中是开发假设；生产规则和权限由业务确认并版本化。

## 2. 多零件数据模型

评估颗粒度为 `供应商 × 零件 × 工厂 × 风险维度 × 时间范围`。供应商财务、司法和舆情继续属于主体级风险，与零件级运营风险分别展示。

| 数据对象 | 业务颗粒度 | 必须具备的关联与范围 |
| --- | --- | --- |
| 供应商 | 一个正式主体 | supplier_id、supplier_code、责任采购员 |
| 零件 | 一个物料主数据项 | material_id、material_code、规格/版本、单位、关键件属性 |
| 供货关系 | 一家供应商向一个工厂供应一种零件 | supplier_id、material_id、plant_id、资格/配比、有效期 |
| 交付计划 | 一个订单行的一次计划交付 | 源行 ID、schedule_id、物料工厂、数量、要求窗口 |
| 到货事实 | 一次有效到货记录 | receipt_id、关联计划、数量、时间、状态；允许分批 |
| 检验事实 | 一个批次的一次有效检验结果 | 供应商、零件、工厂、批次、初检/复检、数量、日期和版本 |
| 库存快照 | 一个工厂零件在一个库位的时点余额 | 零件、工厂、库位、可用量、锁定/隔离量、时间 |
| 需求计划 | 一个工厂零件在一个时间段的需求 | 零件、工厂、需求量、周期、计划版本 |
| 分配供给 | 一笔供货对一个工厂零件需求的分配 | 供应商、零件、工厂、批次/运输单、分配量、预计可用时间 |
| 风险结果 | 一个目标一个维度的时段/时点评估 | 范围引用、指标、规则版本、等级、覆盖与证据 |
| 行动计划 | 明确范围内的处理方案 | 供应商、零件、工厂、风险/单据引用、参数、责任人、审批/回执 |

工厂库存和需求本身没有供应商维度，通过供货关系和供给分配关联供应商。不能把同一工厂零件库存复制到多个供应商后累加，也不能把供料压力直接作为供应商违约证据。供应商库存、工厂库存、在制品和在途分别存储，只有确定归属和可用时间的供给才进入供需预测。

业务清单中的订单行号标为无。接入时必须取得稳定源行 ID 或已验证的唯一关联键，不能直接假定“订单号 + 物料号”唯一。关联歧义的记录进入待核对，不形成正式按零件结论。

所有记录具有 source_record_id、source_system、observed_at、collected_at、单位、校验状态和数据来源模式；业务代码映射到内部稳定 ID。日期带时区。开发基准时点固定为 `2026-10-13T09:00:00+08:00`，生产评估采用实际 as_of。

## 4. 场景一：交期持续恶化，准备备用供货

### 4.1 情景

供应商甲提供支架组件，近三个统计周期准时率逐步下降。最近十次拉动交付有三次超出要求窗口；下一笔订单也预计晚到。采购员希望知道延期严重程度、下一笔是否能保障，以及备用方案的增量成本。

### 4.4 指标、规则与答案

| 指标 | 计算 | 结果 |
| --- | --- | --- |
| 当前周期准时率 | 7 / 10 | 70% |
| 环比变化 | 70% - 90% | 下降 20 个百分点；当前周期为截至 10 日的阶段值 |

开发样本规则：当前周期准时率低于 80% 为高风险；80% 至不足 95% 为中风险；至少 95% 为低风险。最低样本量为十次完成交付；不足时显示样本不足。此规则只用于本开发样本。

期望主回答：“最近十次交付三次迟到，准时率为 70%。下一笔 1,000 件订单预计超出要求窗口四小时。建议核实预计到货时间，并准备备用供货；备用方案预计增加 1,500 元成本。”

### 4.5 行动和后续效果

提案 `DEV-ACT-D01`：将下一笔 1,000 件需求交由开发样本备用供货商保障，开发样本预算上限 1,500 元；需要采购经理审批。重新分配前需模拟确认原订单取消或减量，避免双重供货。

审批后仅表示方案获批；原来的 70% 准时率保持不变。切换到 `after_simulation` 后，时钟为 2026-10-24 09:00：模拟下一笔按时到货，后续十次分配给备用供货商的交付十次准时，形成独立的后续保障记录。该 100% 描述备用方案的十次仿真交付，不表示主供恢复，也不改写历史周期。

### 5.5 行动和后续效果

提案 `DEV-ACT-Q01`：维持 480 件隔离，对后续批次加严检验；质量工程师牵头 8D 验证，采购员负责催办。开发样本增量检验费用设为 1,000 元，需要采购经理及质量负责人确认。

审批本身不改变检验结果。在未来仿真阶段，时间为 2026-10-21 09:00：新增一个独立验证批次 `DEV-QB-005`，10,000 件中 9,940 件合格、60 件不合格，合格率为 99.4%。两份整改报告完成本轮验证，状态为“持续观察”，还需另一个验证周期决定是否正式关闭。

主回答只声明“仿真验证批次有所改善，仍需持续观察”，不声明已经证明根因或彻底消除问题。旧周期 480 件不合格和 95.2% 保留。

| 主供到货前缺口 | 2,000 - 1,500 | 500 件 |
| 理论供料空档 | 48 - 36 | 12 小时 |
| 备用采购数量 | 500 件缺口 + 300 件开发样本缓冲 | 800 件 |

十二小时是按均匀耗用、固定 ETA、无替代库存和即到即用假设得到的供料空档，不能直接作为真实停线时长。页面用“预计供料空档 12 小时”，可在解释中说“在本开发样本假设下可能影响生产”。

主供单价 100 元/件，备用单价 108 元/件，紧急运输费 1,600 元。增量成本 `800 × (108 - 100) + 1,600 = 8,000 元`；备用采购总支出为 `800 × 108 + 1,600 = 88,000 元`。两者分别展示，避免混淆。

本场景规则：未来 72 小时内出现明确的预计供料缺口为高风险；无缺口但当前覆盖不足两天为中风险；当前覆盖至少两天且未来 72 小时无缺口为低风险。主供每日 800 件产能不直接推出缺口，因为未提供实际分配或排产承诺。

期望主回答：“当前 1,500 件库存按每日 1,000 件需求可撑 1.5 天，主供补货预计两天后到。按本开发样本假设，补货前缺口 500 件、供料空档 12 小时。建议从已确认的备用来源桥接 800 件，预计增量成本 8,000 元。”

### 6.4 行动与仿真轨迹

提案 `DEV-ACT-I01`：备用来源桥接采购 800 件，要求在 2026-10-14 09:00 到达；采购经理审批 88,000 元总支出及 8,000 元增量成本。开发样本设定后续采购计划允许吸收这 800 件，避免无解释的库存积压。

| 时间 | 无措施的物理库存 / 累计未满足需求 | 获批并按计划模拟到货的库存 |
| --- | --- | ---: |
| 2026-10-13 09:00 | 1,500 / 0 件 | 1,500 件 |
| 2026-10-14 09:00，桥接到货前 | 500 / 0 件 | 500 件 |
| 2026-10-14 09:00，桥接到货后 | 500 / 0 件 | 1,300 件 |
| 2026-10-14 21:00 | 0 / 0 件 | 800 件 |
| 2026-10-15 09:00，主供到货前 | 0 / 500 件 | 300 件 |
| 2026-10-15 09:00，主供到货后 | 1,800 / 500 件 | 2,100 件 |

物理库存不显示负数；无措施时的 500 件短缺独立展示。本场景在 2026-10-15 09:00 的仿真观测结果：桥接方案避免了预计供料空档，库存 2,100 件，覆盖 2.1 天。以后是否充足还需新的需求与到货计划，不能据该时点直接认定未来 72 小时低风险。

## 8. 指标口径、规则与供应商汇总

前述准时率按完成交付计划计数；足量准时以窗口内累计到货达到要求数量为准。生成分批到货数据时取达到要求数量的时刻，不以第一车到厂代表整笔完成。取消计划剔除，未交/逾期计划另外统计，分批到货不扩充分母。

质量采用一次检验合格率，复检和返工单独保留，不能覆盖初检结果。汇总使用分子、分母加总，不平均各批百分比。采用来源平台汇总指标时保留原口径；分母未知则显示来源指标和覆盖不足，不声称已独立重算。

前述风险阈值为开发用规则草案。生产上线前要按物料类别、关键件属性、工厂要求和历史回放确认，并保存生效时间和规则版本。严重质量事件、整改逾期、未交超期、未来迟到和库存缺口分别作为触发项，不由单一百分比覆盖。

供应商总览展示唯一零件数、工厂数、有效供货关系数、受影响零件/关系数、各维度最高已验证等级和数据覆盖。样本主结论为：支架在工厂一交期异常、密封圈质量异常、控制器存在工厂供给压力；定位销及支架在工厂二当前正常。

暂不把财务、司法与运营维度混合成一个新综合分数。总体百分比只作背景，零件级告警保留。缺失、过期、关联歧义、分母不足均产生数据不足/待核对状态，不形成低风险结论。

## 9. 页面、自然语言与行动闭环

业务路径：供应商总览 → 零件列表 → 零件工厂详情 → 订单/检验/库存证据 → 处理方案 → 审批 → 执行回执 → 效果验证。

零件列表展示编码、名称、工厂、三维风险指标、更新时间和覆盖情况。详情展示趋势、源单据、原因与待验证假设、影响及建议。行动卡片明确限定零件、工厂和关联单据，显示执行人、期限、预算、审批及真实回执。

支持提问：“供应商甲哪些零件有风险？”、“只看工厂一的支架”、“密封圈有问题，其他零件是否正常？”、“比较支架在两个工厂的供货情况”。未指定工厂且存在多个工厂时按工厂返回或澄清，不擅自合并。

审批只改变审批状态；外部业务执行成功需持久化回执，后续风险变化由新事实重新评估。执行完成与风险解除分别处理，不改写历史事实。开发样本的后续观测按独立 as_of 回放；生产效果采用真实的新记录。

## 10. 与当前项目融合

新增运营风险请求契约携带 supplier_ids、material_ids、plant_ids、dimensions、period_start、period_end、as_of；不直接修改当前仅 company_name 的工具或现有公开 API 返回结构。库存供给作为新增运营能力，保持旧质量/交付调用兼容。

活动聊天继续进入唯一 Harness，工具注册统一输入输出、证据与审批策略，通过 ToolExecutor 执行。本次请求的 execution_context 只加载一次，解析、规划、执行和追问共用同一快照；当前明确零件与工厂约束优先于旧对话记忆。

企业主体与零件工厂评估范围分开：复用现有主体实体和供应商引用收集器，风险任务、Evidence 与 Claim 绑定供应商/零件/工厂/维度/周期，避免另一零件的证据污染结论。一个目标完成不能覆盖其他目标的数据缺口。

新增业务服务和仓储保持框架无关，不在 service 中引入 LangGraph。PostgreSQL 保持会话、运行、任务、提案与审批执行控制状态的事实源；MongoDB 保存业务明细、快照与证据，遵循已有权威数据归属。

权限先继承正式供应商责任范围，零件和工厂限制进一步收窄。质量、制造等协同角色需明确权限配置；供应商读取权限不自动授予所有工厂执行权限。资格和预算门禁限定实际行动范围。

合成样本带 dataset_id、data_mode=synthetic、decision_usable=false，隔离于正式事实和告警；不将其标成 real，也不改变现有 synthetic 证据门禁。业务术语和功能入口按正式项目设计，数据来源标记保留真实性。

## 11. 数据接入与上线要求

| 能力 | 业务清单初步已有数据 | 必须验证或补充 |

先完成领域模型和来源适配接口，用开发样本验证多零件链路，再按数据条件逐项接入交付、质量和库存供给。某维度未达到真实数据条件时保留数据不足状态，不用合成值填补生产缺口。

正式行动先支持工作流派发或人工完成回执。直接修改采购/生产业务系统需明确接口、授权、审批、幂等与失败恢复规则。库存供料空档不能直接当作真实停线分钟，需接工厂排产与 BOM/消耗计划后再扩展影响计算。

上线前需完成源数据对账、指标/阈值业务确认、零件工厂关联校验、权限隔离、缺失过期处理、告警去重、审批回执与恢复验证。

## 12. 开发数据生成与验收范围

3. 交期明细导出延期 540 分钟、平均 180 分钟、最大 240 分钟；下一笔 ETA 不混入历史指标。
