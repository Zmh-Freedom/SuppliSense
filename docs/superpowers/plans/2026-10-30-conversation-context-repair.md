# 会话上下文修复与职责收敛计划

> 执行状态：待评审，尚未实施。本文是实施计划和设计基线；执行时按当前工作区代码复核路径、测试和未提交改动。执行方式由用户决定；不得仅因本文预设方式而新建任务或并行代理。

**目标：** 消除无业务任务状态导致的跨轮失败与错误重复展示，并以真实的状态往返测试保障聊天上下文；在此基础上分阶段厘清对话理解、业务决策、执行与证据、会话保存的职责。

**架构方向：** 普通聊天和只读业务请求继续使用唯一 LangGraph Harness；用户输入先形成可追溯的对话理解，只有有业务意图时才形成可执行任务。持久化状态的无任务值为 `null`；现有运行时 `current_task` 字典调用方通过兼容适配逐步迁移，不得在未完成调用方排查前直接把所有运行时值改成 `None`。模型提出的实体是候选，正式主体、权限、证据和写操作审批由业务边界确认。

**技术栈：** FastAPI、Pydantic v2、LangGraph、PostgreSQL、MongoDB、Redis、React、TypeScript、pytest、Vitest。

**设计来源：** 本文“职责与契约”“范围和阶段门”及本聊天已确认的责任划分；实施阶段若发现会改变用户体验或数据迁移语义的重大分歧，先更新方案供用户评审。

## 职责与契约

1. **对话理解：** 消费本轮消息、受限的最近历史、已确认会话事实、待澄清事项；输出意图候选及其来源/不确定性。模型输出不直接形成已核实供应商身份。
2. **业务决策：** 对无业务任务、需澄清、只读任务、写操作分别决策。用户当轮明确内容优先于无关的旧任务；不能为修复 `none` 默认创建寻源任务或复用旧供应商。
3. **执行与证据：** Harness 消费 API 为本轮准备的同一上下文，不在图内重新加载；候选主体先核验再查询，结果保留来源和缺失状态。加入/移出监控走持久化 Supervisor、Proposal 和人工确认。
4. **保存与恢复：** PostgreSQL 中用户归属的 Session/Turn/Run 和状态为控制面事实；正常终态中最终事件、答案和 next_context 保持现有事务一致性；Mongo 展示投影、浏览器 localStorage 不替代它。
5. **无任务语义：** 上游意图字段仍可用 `"none"` 表示未识别业务意图；序列化的 `ConversationState.current_task` 用 `null` 表示没有可执行任务；读到历史 `{"task_type":"none", ...}` 时只在无目标、无维度、无待恢复业务字段时视为无任务。若存在目标、维度、寻源要求、待澄清或审批信息，不得静默丢弃或猜测业务任务类型，必须保留并走可诊断的澄清/兼容路径。具体迁移映射先以失败测试固定，遵循现有确认过的业务语义。
6. **引用范围：** `none` 兼容仅处理业务状态，不清除已确认供应商、历史、待澄清事项或审批；明确换题与目标切换按现有语义处理并由回归验证，不能一律沿用上一轮。

## 审阅焦点

- 历史 `none` 附带待澄清、实体、要求或审批数据：不得清空或误执行；覆盖 Task 1、3。
- 本轮明确换题/换供应商：不能因兼容状态而沿用旧主体；覆盖 Task 1、3。
- 未确认简称/多主体“它”：不得猜测并调用业务工具；覆盖 Task 3。
- SSE 失败后重复、刷新、断线或旧事件重放：每个错误只出现一次，不丢失可恢复状态；覆盖 Task 2、4。
- 非所属会话、重复提交、写操作未审批：不得读他人状态或执行副作用；覆盖 Task 3、4。
